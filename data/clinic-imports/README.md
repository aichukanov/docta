# Записи об импорте клиник

Один JSON на клинику: `data/clinic-imports/<clinic-slug>.json`, имя файла совпадает
с `clinics.slug`.

## Зачем

SQL-файл отвечает на вопрос «что вставить». Он **не** отвечает на вопросы, которые
встают при следующем обновлении той же клиники:

- откуда взялась каждая услуга — какая фраза источника во что сопоставлена;
- что сознательно **не** заводили и почему (иначе каждое обновление заново
  упирается в те же спорные места);
- какие источники проверяли, когда, и читаются ли они машинно;
- где импорт уже применён и какие id получил.

Всё это сейчас живёт в комментариях SQL — читаемо человеком, но не диффается и
теряется при перегенерации файла. Запись выносит это в структуру.

## Чем это НЕ является

- **Не источник правды для БД.** Что реально выполняется — только SQL из
  `server/sql/`. Запись описывает импорт, а не заменяет его.
- **Не вход генератора.** Пока SQL пишется руками. Формат намеренно оставлен
  таким, чтобы генератор можно было прикрутить позже, но сейчас его нет, и
  расхождение JSON с SQL ничем не ловится, кроме ревью.
- **Не общий индекс.** Индекса нет сознательно: общий файл на всех молча теряет
  правки при параллельной работе, а листинг каталога и так даёт список.

## Обязательные поля

| Поле | Что кладём |
| --- | --- |
| `schemaVersion` | `1` |
| `slug`, `name`, `city`, `googlePlaceId` | идентификация; `googlePlaceId` = `null`, если места в Google нет |
| `sql` | пути к SQL-файлам в порядке применения |
| `status` | `generated` (дата), `appliedLocal` / `appliedProd` (дата или `null`), `clinicId`, `doctorIds` |
| `sources` | что читали: `type`, `ref`, `collected`, `machineReadable`, `note` |
| `coverage` | по каждому блоку данных: заполнен, пуст или недоступен, и почему |
| `catalogAdditions` | записи, которые импорт добавил в общий каталог (услуги, категории) |
| `services` | `nameEn` (ключ в `medical_services`) + `source` (дословная фраза источника) |
| `doctors` | `slug`, `nameSr`, `specialtyIds`, `position`, `services`, `hasBio` |
| `excluded` | что не завели: `source` + `reason` |
| `openQuestions` | что требует решения человека |

## Правила

1. **`source` — дословная фраза источника**, не пересказ. Именно она позволяет при
   обновлении понять, изменился ли источник, или только наше сопоставление.
2. **`services[].nameEn` должен совпадать со списком в SQL** до последней строки.
   Разошлись — SQL прав, запись чинят по нему.
3. **`status.clinicId` и `doctorIds` заполняются ПОСЛЕ применения**, из блока
   VERIFICATION в конце SQL. До этого — `null`.
4. **`excluded` не чистим при обновлении.** Это протокол принятых решений: если
   позиция появилась в источнике позже, её переносят из `excluded` в `services`
   с новой датой, а не удаляют молча.
