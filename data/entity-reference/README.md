# Справочный контент для страниц услуг и анализов

Черновое хранилище текстов для контент-слоя из [[service-reference-content]] (`prd/service-reference-content/`). Позже — миграция в SQL, аналогично `medical_service_tariffs` в [[fzocg]].

## Файлы

- `lab-tests*.json` — справки для `lab_tests` (`pages/labtests/[labTestSlug]/`)
- `medical-services*.json` — справки для `medical_services` (`pages/services/[serviceSlug]/`)
- `TODO-worklist.md` — что ещё не написано, разбито на тиры по приоритету
- `_roster-lab-tests.json`, `_roster-medical-services.json` — позиции без справки
  (название во всех локалях, категории, покрытие клиниками). Файлы с `_` сборщик
  не читает: префикс не совпадает. Пересобрать —
  `node scripts/entity-reference/build-reference-roster.mjs [--min-clinics 5]`

## Скрипты

| скрипт | что делает |
|---|---|
| `build-reference-roster.mjs` | ростер «что ещё без справки» из БД: исключает написанное (по JSON, не по БД — локальная отстаёт) и выбывающие половинки непринятых миграций дедупликации |
| `validate-reference-batches.mjs` | проверка батчей перед сборкой SQL: слаг есть в БД, все локали и поля на месте, нет `|`, нет экавицы в `sr`, нет числовых референсов, нет копипасты между позициями |
| `list-latin-tokens.mjs` | латинские токены в сербских текстах — кандидаты в защищённый список |
| `generate-sr-cyrl.mjs` | заполняет `sr_cyrl` транслитерацией из `sr` (список — `scripts/common/sr-cyrl-protected.mjs`) |
| `build-entity-reference-sql.mjs` | собирает `server/sql/migrations/insert-entity-reference-info.sql` |

Порядок: написать батчи → **сверить названия с БД** (см. ниже) →
`validate-reference-batches.mjs` → `list-latin-tokens.mjs` и правка защищённого списка →
`generate-sr-cyrl.mjs` → `build-entity-reference-sql.mjs` → применяет SQL пользователь.

### ⚠️ Ростер живёт до следующей миграции названий

Волна 3 налетела на это в полный рост: миграции 036/037 переименовали **345 позиций**
уже после сборки ростера, и часть переименований изменила смысл, а не формулировку.
Пять карточек прижигания кожных образований были разведены по размеру образования —
а градация оказалась по их количеству (1/2/3/4/5+). Карточки пришлось переписывать.

Поэтому перед сборкой SQL сверяй `name_ru`/`name_en` во входных батчах с текущей БД:
если имя изменилось сильно (мало общих слов), карточку надо перечитать, а не досылать
как есть. Для ненаписанных батчей проще обновить входные файлы из БД.

### После транслитерации — глазами по кириллическим аббревиатурам

Прописные кириллические последовательности в `sr_cyrl` — быстрый способ найти сломанное:
правильные (ДНК, ПЦР, ЕКГ, ХОБП, ОРЛ, МР, ЛДЛ) соседствуют с мусором вроде «БРЦА1»,
«МТХФР», «ЦОВИД-19», «ЦРП», «Хер2», «МЦХЦ». Всё, что выглядит как транслитерированная
латинская аббревиатура, добавляется в `scripts/common/sr-cyrl-protected.mjs`, после чего
`sr_cyrl` у затронутых карточек удаляется и генерируется заново.

### ⚠️ Новый батч — НОВЫЙ ФАЙЛ, не дописывать в общий

Сборщик подхватывает **все** файлы по префиксу (`medical-services-batch-08.json`,
`lab-tests-batch-03.json` и т.п.), поэтому каждый батч/сессия пишет в свой файл:

```
data/entity-reference/medical-services-batch-08.json
```

Так над контентом можно работать в несколько окон одновременно. Если все дописывают
в один `medical-services.json`, правки затираются **молча**: файл остаётся валидным
JSON, просто часть карточек исчезает — и это не всплывёт до сверки с продом.

Дубли по `slug` между файлами сборщик ловит и падает с ошибкой (значит, два батча
взяли одну позицию — надо развести). Порядок чтения файлов алфавитный, SQL
получается детерминированным.

## Схема (1 элемент массива)

```json
{
  "slug": "complete-urinalysis",
  "entity_type": "lab_test",
  "translations": {
    "ru": {
      "what": "1 фраза — что это",
      "how": "как физически проводится, сколько занимает",
      "when": "типичные показания",
      "prep": "условия подготовки",
      "abnormal": "нейтрально — «может быть связано с ...», обязательно с отсылкой к врачу"
    }
  }
}
```

`slug` — должен совпадать с `lab_tests.slug` / `medical_services.slug` в БД (связь по слагу, не по id — id в JSON не хранится).

`translations` — по мере перевода добавляются ключи `en`, `sr`, `sr_cyrl`, `de`, `tr` с тем же набором из 5 полей. Отсутствие локали в `translations` = перевод ещё не готов, не показывать/фолбэк на `ru` — решается на этапе вывода.

**`sr_cyrl` не переводится отдельно** — генерируется механической транслитерацией из `sr` (латиница→кириллица, тот же принцип, что в `common/serbian-transliteration.ts`) скриптом `scripts/entity-reference/generate-sr-cyrl.mjs`: он заполняет только отсутствующие `sr_cyrl` (пересобрать все — `--force`). Международные лабораторные обозначения нужно защищать от транслитерации явным списком (`PROTECTED_LATIN_TOKENS` в этом скрипте) — иначе получается мусор («HbA1c» → «ХбА1ц») или омографы с обычными сербскими словами («PSA» → «ПСА», совпадает с род. падежом слова «пас»/собака). Устоявшиеся сербские кириллические аббревиатуры (ХИВ, ЕКГ, ХОБП, МР, ОРЛ, АСТ, АЛТ, ЛДЛ, ХДЛ) транслитерируются нормально — в список защиты не входят. При добавлении новых карточек с незнакомыми латинскими аббревиатурами — проверять результат sr_cyrl глазами, а не доверять транслитерации вслепую.

Дисклеймер («информация не заменяет консультацию врача...») в данных не хранится — единая i18n-строка на уровне шаблона страницы, показывается для каждой карточки.

## YMYL-правила (см. подробно в PRD)

Без числовых референсов, без диагностических формулировок («X означает болезнь Y»), только «может быть связано с» + отсылка к врачу.
