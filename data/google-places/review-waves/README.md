# Проходы по отзывам Google Maps

Журнал съёмов отзывов с карточек Google: что снимали, сколько пришло, что
применено. Как снимать — скилл `gmaps-reviews` (`.claude/skills/`), здесь —
когда и что уже сделано.

## Когда проходить

| Проход | Периодичность | Кого |
| :-- | :-- | :-- |
| **Обновление** | раз в 3 месяца | клиники, у которых отзывы в базе уже есть |
| **Новые** | после каждой волны добавления клиник | клиники без отзывов, у которых на карточке они есть |

За полгода между съёмами у средней клиники прибавляется единицы отзывов, у
крупных — десятки; чаще раза в квартал проход почти ничего не даёт, а занимает
2–3 часа браузера.

**Следующее обновление: 2027-01.**

## Как пройти

1. Очередь — от клиник **в базе**, не от каталога Places:
   `build-review-targets.mjs` смотрит на `data/google-places/` целиком и тащит
   салоны, ветклиники, аптеки. Для обновления цели — `jsonPath` конфигов
   `data/review-import-configs/` у клиник с отзывами; для новых — клиники без
   отзывов, сопоставленные с карточками. Файл очереди —
   `<дата>-<проход>.json` в этой папке, состояние прогона рядом,
   `<дата>-<проход>.state.jsonl` (`run-queue.mjs --state`).
2. Сессия — на нашей карточке:
   `check-session.mjs --place-id ChIJ1VxH0hTrTRMRyy8OYWPH7kU`.
3. `run-queue.mjs --targets <очередь> --state <состояние>`.
4. `merge-gmaps-dump.mjs --dry-run`, затем без него.
5. SQL: для обновления — `generate-reviews-sql.mjs <конфиг> --since <дата
   прохода>` по каждому конфигу, для новых — без `--since`. Склеить в один
   файл `server/sql/reviews-google/wave-<дата>-<проход>.sql`.
6. Строку в журнал ниже; в `data/review-import-progress.json` —
   `lastCollectedAt`.

## Проверка дублей — до SQL

Новый отзыв — тот, чьего id нет в базе. Каждый такой сверить с базой и со
старыми отзывами файла **по автору** (contributor id) и **по тексту с
оценкой**, не только по id и дате:

- автор с новым отзывом на той же карточке, где его старого больше нет, —
  отзыв переписан и получил новый id: старую строку обновить, а не добавлять
  вторую (2026-10-30: Marko Milić, 5★ → 1★);
- тот же автор на разных карточках одной клиники (Klinički centar держит
  три: основная, Urgentni, Institut za bolesti djece) — разные отзывы.

После применения — те же два запроса по базе: автор дважды у клиники,
одинаковый текст+оценка у клиники.

## Грабли

- **Двойные файлы в каталоге.** У 41 места по два файла в разных папках
  городов (`berane/dom-zdravlja-andrijevica.json` и
  `andrijevica/dom-zdravlja-andrijevica.json`). Слияние пишет в файл,
  на который смотрит конфиг; до 2026-10-30 писало в случайный, и четыре
  клиники первой волны получили по 5 API-отзывов вместо всех.
- **Отступ файлов.** Выгрузки расширения лежат с табами; переписанные двумя
  пробелами дают diff на тысячи строк. Слияние сохраняет отступ файла.
- **place_id из hex-пары.** `ChIJ…` — base64url от `0a 12 09 <hi LE 8 байт>
  11 <lo LE 8 байт>`, где `0x<hi>:0x<lo>` — `placeIds.hexId` выгрузки. Так
  2026-10-30 получены id 14 файлов без них; каждый проверен заходом в Карты.
  До этого их отзывы лежали в базе как `places/undefined/reviews/…` —
  ключи переведены в той же миграции.
- **Конфиги с числовым `clinicId`** (старые) совпадают с продом; у новых —
  `clinicSlug`. Генерировать в отдельный `outputPath`, иначе `--since`
  перезапишет полный SQL клиники частичным.
