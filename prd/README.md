# Product Requirements Documents (PRD)

Эта папка содержит детальные PRD документы для функциональности проекта docta.me.

## Структура

Каждый PRD организован в виде модульной структуры:

- **Главный файл** (`index.md`) - навигация и обзор
- **Секции** - отдельные файлы для каждой части документа
- **Итерации** - отдельная папка с детальным описанием каждой итерации разработки

Каждая итерация:

- Может быть выполнена LLM автономно
- Требует ручной проверки перед переходом к следующей итерации
- Содержит четкие критерии приемки (acceptance criteria)
- Включает технические детали реализации

## Формат PRD

Каждый PRD использует модульную структуру с папкой, содержащей `index.md` и отдельные файлы секций.

Проект разделен на несколько независимых PRD для лучшей управляемости и возможности параллельной разработки.

### 🚨 [silent-200-index-hygiene/](silent-200-index-hygiene/) — Тихие 200 вместо 301/404/500

**Приоритет:** P1 | **Статус:** 🟡 3.5/4 | ✅ **итерации 1–3 на проде** (выкатано и проверено 2026-07-30, коммит `6acf400`). У итерации 4 готов код: осталось задеплоить, отправить IndexNow и отключить Cloudflare Managed robots.txt

Один класс дефектов: при сбое или отсутствии данных приложение деградирует тихо и отдаёт 200 там,
где обязано отдать 301/404/500. Поисковик 500 повторит, а 200 запомнит навсегда.

Измерено на срезе индекса Яндекса (1434 страницы, выгрузки в `data/yandex/`):
**602 URL с числовыми ID = 42% индекса** — из-за `catch → null` в `slug-redirects.ts` редирект
молча не срабатывал во время июньской аварии БД; soft-404 на catch-all
(`pages/[...not-found].vue` отдавал 200 без title, без noindex, с canonical на несуществующий
URL); 15 из 17 статей вне sitemap (в индексе ровно те две, что в sitemap есть); дубли canonical
по порядку параметров и `?tab=`. Пятая заявленная находка (страница 500 отдаётся с 200) при
проверке **опровергнута** — Nuxt отдаёт честный 500.

Итерации: 1 — честные коды ответа ✅ (самая ценная, трогает middleware на каждом запросе),
2 — sitemap ✅, 3 — canonical ✅, 4 — IndexNow и robots.txt 🟡 (код готов; отправка возможна только после деплоя — IndexNow проверяет владение доменом, скачивая ключ-файл).

Ревизия 2026-07-30 (в рамках ревью SEO-аудита): код и тесты на месте, **в тот же день выкачено
на прод и проверено** — числовые URL 301-ятся, soft-404 отдаёт 404 без canonical, sitemap
13 591 → 13 640 (ровно +49), фасеты не схлопнулись. Нашлись два проявления того же
класса вне скоупа PRD — невалидные значения фильтров (`?specialtyIds=99999` отдаёт полный
листинг с self-canonical на мусорный URL) и `?sort=` на подстраницах клиник; итерация 3 их не
закрывает, потому что нормализует порядок параметров, а не значения. Записаны в аудит как 7d/7e.
Плюс закрыта смежная находка: внешние 301 с 8 выкупленных доменов теперь ведут прямо на слаг,
а не на числовой ID.

Побочная находка, крупнее этой PRD: `getConnection()` вызывается напрямую в ~80 файлах и
`try/finally` нет ни в одном из проверенных — соединение освобождается только на happy path.
Похоже на реальную причину падений прода, см. «Открытые вопросы» в
[PROGRESS.md](silent-200-index-hygiene/PROGRESS.md).

## Создание нового PRD

### ⭐ Рекомендуемый подход: Модульная структура (как reviews/)

**Создавайте новые PRD по аналогии с [reviews/](reviews/)** - используйте модульную структуру с папками и отдельными файлами.

#### Шаг 1: Создайте структуру папок

```
prd/
└── <название-фичи>/              # Например: notifications/, payments/, reviews/
    ├── index.md                   # Главная страница с навигацией
    ├── PROGRESS.md                # 📊 Отслеживание прогресса и статусов
    ├── 01-overview.md             # Обзор, цель, контекст
    ├── 02-requirements.md         # Функциональные и нефункциональные требования
    ├── 03-architecture.md         # Стек, API endpoints, компоненты, диаграммы
    ├── 04-database.md             # Схема БД, миграции (если применимо)
    ├── 05-risks-and-metrics.md    # Риски, метрики успеха, вопросы
    └── iterations/                # Папка с итерациями разработки
        ├── README.md              # Обзор всех итераций с таблицей статусов
        ├── iteration-01-*.md      # Итерация 1
        ├── iteration-02-*.md      # Итерация 2
        └── ...                    # И так далее
```

#### Шаг 2: Скопируйте шаблон из reviews/

```bash
# Создайте новую папку
mkdir prd/<название-фичи>

# Скопируйте структуру из reviews/ как основу
cp -r prd/reviews/* prd/<название-фичи>/

# Адаптируйте содержимое под вашу фичу
```

#### Шаг 3: Заполните секции

1. **index.md** - создайте навигацию по всем секциям и итерациям
2. **PROGRESS.md** - создайте файл для отслеживания прогресса (см. [reviews/PROGRESS.md](reviews/PROGRESS.md))
3. **01-overview.md** - опишите цель, контекст, предположения
4. **02-requirements.md** - перечислите FR и NFR, определите scope
5. **03-architecture.md** - опишите API, компоненты, диаграммы
6. **04-database.md** - если нужны изменения БД, опишите схему
7. **05-risks-and-metrics.md** - оцените риски, определите метрики
8. **iterations/** - разбейте работу на логические итерации

#### Шаг 4: Структурируйте итерации

Каждая итерация должна содержать:

- ✅ Цель и зависимости
- ✅ Список задач
- ✅ Технические детали (примеры кода, файлы)
- ✅ Критерии приемки (AC-1, AC-2, ...)

✅ **Масштабируемость** - легко добавлять итерации  
✅ **Читаемость** - меньше когнитивной нагрузки  
✅ **Совместная работа** - несколько человек могут работать параллельно
