# Задача: KitPagination — номера страниц настоящими ссылками

**Статус: 🟢 сделано 2026-09-08.** Что получилось и чем отличается от брифа —
в конце файла.

Самостоятельный бриф для агента дизайн-системы. Развёрнутый разбор — в
[iteration-02-catalog-filters.md](iterations/iteration-02-catalog-filters.md),
здесь то, что нужно, чтобы взять и сделать.

## Зачем

`components/pagination.vue` использует `el-pagination`, а Element Plus рисует
номера страниц как `<li class="number">` — без `href`. Следствие: страницы
`?page=2` и дальше **существуют, отдают 200 и self-canonical, но недостижимы
для поисковика без исполнения JS и отсутствуют в sitemap**. Вес с листингов
вглубь каталога не передаётся вообще.

Единственное упоминание следующей страницы в разметке — `<link rel="next">` в
`<head>`, и оно не считается: Google не поддерживает `rel=next/prev` с 2019
года.

Это единственная задача итерации 2 с SEO-нагрузкой, а не только с весом
бандла. Правка ждала дизайн-систему сознательно: чинить это поверх Element Plus
значило бы перекрывать чужую разметку, что противоречит конвенции «контролы
только из библиотеки».

## Что сделать

Заменить внутренности `components/pagination.vue` компонентом кита:
`prev / номера / next`, до 5 номеров, состояние disabled.

Каждый номер страницы обязан быть `<a href>` с настоящим адресом.

## Откуда брать адрес

**Не собирать URL самостоятельно.** Готовая сборка уже есть — `buildUrl`
внутри `paginationLinks` в `components/list-page.vue`: она идёт через
`getCanonicalUrl` из `common/url-utils.ts`.

Причина принципиальная: своя склейка разъедется с canonical по порядку
параметров, и вернутся дубли, против которых затевалась итерация 3 PRD
«Тихие 200» (`prd/silent-200-index-hygiene/`). Адрес в `href` и адрес в
`rel=canonical` целевой страницы обязаны совпадать побайтово.

Практически это означает новый необязательный проп у `pagination.vue` —
построитель ссылки вида `(page: number) => string`, который передаёт
`list-page.vue`. Это единственная обёртка, чей внешний API расширяется
(зафиксировано в `02-requirements.md`, FR-6).

## Обязательное требование: переходы остаются клиентскими

`<a href>` нужен краулеру, но человек не должен получать полную перезагрузку.

- левый клик без модификаторов → `preventDefault` и прежний
  `update:current-page`;
- Ctrl/Cmd/Shift/средняя кнопка → отдать браузеру, не перехватывать (иначе
  ломается «открыть в новой вкладке»).

## Кто это использует

| Файл | Нужен href |
| --- | --- |
| `components/list-page.vue` | **да** — страница живёт в URL |
| `components/clinic/items-page.vue` | **да** |
| `components/reviews-page.vue` | **да** |
| `components/map/clinic-popup.vue` | **нет** — состояние попапа, не адрес |

У попапа карты страница в URL не отражается, там ссылки не нужны и не нужны
`<a>` вовсе.

## Как проверить

**Только на собранном приложении**, не в `nuxt dev`: важно, что ссылка есть в
серверной разметке.

```sh
npm run build
node .output/server/index.mjs   # порт задать свободный, напр. PORT=3100
curl -s http://localhost:3100/doctors | grep -o 'href="[^"]*page=2[^"]*"' | head
```

Ожидание: ссылка на вторую страницу есть в HTML **до** выполнения JS.

Приёмка:

1. номера страниц — `<a href>` в SSR-разметке;
2. адрес в `href` совпадает по составу и порядку параметров с `canonical`
   целевой страницы;
3. левый клик не перезагружает страницу, Ctrl-клик открывает новую вкладку;
4. попап карты не изменился;
5. `npx playwright test --project=unit` и `--project=chromium` зелёные.

## Что проверить тестом

В `tests/e2e/` есть готовая обвязка (`tests/utils/http.ts`: `visit`,
`fetchText`, `waitForHydration`). Стоит добавить проверку, что на листинге в
серверной разметке есть ссылка на вторую страницу — сейчас такой проверки нет,
и регресс вернулся бы молча.

## Чего делать нельзя

- Собирать URL пагинации своей конкатенацией.
- Оставлять номера не-ссылками «пока что» — тогда задача не решена вовсе.
- Трогать `?page=1`: он избыточен и закрыт `noindex`
  (`components/list-page.vue`, `hasRedundantQuery`). Ссылка на первую страницу
  ведёт на адрес **без** параметра.

## Сделано (2026-09-08)

`KitPagination` в `@ach/ui-kit`, внутренности `components/pagination.vue`
заменены. Внешний API обёртки прежний плюс необязательный `href`.

| Потребитель | href | Источник адреса |
| --- | --- | --- |
| `components/list-page.vue` | да | `buildPageHref` → `getCanonicalPath` |
| `components/clinic/items-page.vue` | да | `getCanonicalPath` поверх `route.query` |
| `components/reviews-page.vue` | да | `buildPageHref` → `getCanonicalPath` |
| `components/map/clinic-popup.vue` | нет | не изменён, рендерит кнопки |

Проверено на собранном приложении (`node .output/server/index.mjs`, порт 3100):
номера — `<a href>` в серверной разметке, адрес совпадает с `rel=canonical`
целевой страницы побайтово на шести листингах, на подстранице клиники и на
странице отзывов, с `?lang=ru` и с фасетом. e2e 207 passed / 3 skipped,
unit 440 passed, `nuxt typecheck` зелёный.

Регресс закрыт тестом: `tests/e2e/seo.spec.ts` → «Пагинация краулится» читает
СЫРОЙ ответ сервера (`fetchText`), а не DOM после гидратации — в браузере
ссылки появились бы в любом случае. Признак «вторая страница вообще есть» —
`rel=next` в `<head>`: он считается другим кодом, поэтому годится как
независимая проверка (у страховых компаний всего одна страница, и раздел
корректно пропускается).

### Отличия от брифа, принятые сознательно

**`getCanonicalPath` вместо `getCanonicalUrl`.** Адрес по-прежнему берётся
у канонической функции, но в разметку уходит без домена: `getCanonicalUrl`
теперь просто дописывает `SITE_URL` к `getCanonicalPath`, так что разойтись
они не могут — это одна и та же сборка. Абсолютный адрес в теле страницы
уводил бы из локальной сборки и из e2e на прод.

**Многоточие неинтерактивно.** В Element Plus точки прыгали на ±5 страниц,
превращаясь в стрелки при наведении. Механика скрытая; восстанавливать её
не стали. Раскладка пейджера в остальном повторена один в один: первая и
последняя страницы видны всегда, между ними до 5 номеров.

**`<nav>` переехал в обёртку.** Раньше он был только у листингов, теперь его
рисует сама `pagination.vue` — landmark получили и подстраницы клиник, и
страницы отзывов. Локальный ключ `AriaPagination` удалён, подписи глобальные
(`i18n/ui.ts`: `Pagination`, `PreviousPage`, `NextPage`, `PageN`, 6 локалей).

**Тач-цель 44px** на `(hover: none) and (pointer: coarse)` — NFR-6. На десктопе
метрика Element Plus (32px) сохранена.

## Довесок: canonical отзывов сведён к общей функции (2026-09-08)

Найденное по ходу расхождение решено сразу (решение юзера). Своя склейка
canonical в `reviews-page.vue` удалена: страница больше НЕ регистрирует
`rel=canonical` вовсе — его ставит `app.vue` той же `getCanonicalUrl` из тех же
`route.path` и `route.query`. `rel=prev/next` и `href` пагинации собираются
`getCanonicalUrl`/`getCanonicalPath`.

Дубликат чинил не одну ошибку, а две, и обе — молча (ключ `canonical` тот же,
setup дочернего компонента идёт после `app.vue`, поэтому выигрывал он):

1. **Порядок параметров.** Отзывы канонизировались в `?lang=ru&page=2`, всё
   остальное — в `?page=2&lang=ru`. При этом hreflang этим же страницам ставил
   `app.vue` канонической функцией: self-canonical и языковые версии указывали
   на РАЗНЫЕ адреса одной страницы.
2. **`?sort=` выбрасывался из canonical.** На отзывах сортировка меняет состав
   конкретной страницы пагинации, поэтому `sort` и внесён в allowlist
   (`common/url-utils.ts` прямо это оговаривает). А canonical сводил
   `?sort=rating_low&page=2` к `?page=2` — к странице с другими отзывами.

Проверено на сборке: canonical, `hreflang="ru"` и `href` второй страницы
совпадают побайтово; порядок параметров не зависит от порядка во входном URL
(`?lang=ru&sort=newest&page=2` → `?page=2&sort=newest&lang=ru`).

Сторож — `tests/unit/canonical-url.spec.ts`: `rel=canonical` регистрирует
РОВНО один файл, `app.vue`. Сравнение со списком, а не с пустотой, — иначе
сломанный обход давал бы зелёное «лишних нет».

Форма canonical у уже проиндексированных страниц отзывов при этом меняется:
это ожидаемая нормализация (та же, что итерация 3 «Тихих 200» сделала для
листингов), редиректов не требует — старый адрес открывается и канонизируется
в новый.

## Довесок: мобильный пейджер (2026-09-11, кит 0.2.1)

После релиза выяснилось, что на телефоне девять слотов по 44px (428px) не
помещаются и пейджер переносится на вторую строку. Исходный `flex-wrap: wrap`
был ошибкой: так не делает никто.

Что в других системах (смотрел исходники и доки, а не пересказы):

| Система | Узкий экран |
| --- | --- |
| USWDS | `flex-flow: row nowrap`; в SCSS комментарий «Don't show previous and next at mobile. Functionality exists with page buttons» — прячут СТРЕЛКИ, номера оставляют. В доке: «Avoid using Pagination in any context where it would be more than one line long» |
| Primer (GitHub) | `showPages={{ narrow: false }}` — прячут НОМЕРА, остаются Previous/Next |
| eBay | «On smaller screens, more pages will be truncated as the screen width decreases», минимум 5 слотов |
| Ant Design | `simple` — `‹ 4/67 ›`; `responsive` ужимает размер под ширину окна |

Общего в них ровно одно: **одна строка любой ценой, лишние слоты срезаются.**
Кто именно срезается — расходятся.

Выбран вариант «срезать соседей текущей страницы» (юзер, из трёх вариантов на
превью): на ≤600px остаётся `‹ 1 … 4 … 67 ›`. Стрелки и крайние номера живы,
прыжок на последнюю страницу сохранён, тач-цель 44px тоже.

Три вещи, которые пришлось учесть:

- **Прятать можно не любого соседа.** Только того, на чьей стороне уже есть
  многоточие, иначе `1 [3] 5` соврёт, что страниц 2 и 4 не существует. Когда
  страниц мало и многоточий нет, набор и так помещается — прятать нечего.
- **Скрытие CSS-ом, а не пересчётом набора.** `pagerCount`, зависящий от ширины
  окна, разъехался бы с серверной разметкой при гидратации. Ссылки остаются
  в DOM — путь обхода вглубь листинга не страдает.
- **Многоточие ужато до 24px**: оно не кликабельно, тач-цель ему не нужна, а
  40 сэкономленных пикселей решают на 320px.

Замеры на сборке: 320px — 292px в одну строку, 375px — 292px, мало страниц —
236px, десктоп не изменился (320px, высота 32px).

### Хвост: переполнение доставалось странице (кит 0.2.2)

Юзер поймал на 270px: пейджер вылезал за карточку. Замер показал, что дело
не в отступе — сокращённый набор (292px) не помещался в контейнер (254px),
начинался с `x = -11` и растягивал `scrollWidth` документа до 281 при
viewport 270. То есть горизонтальный скролл получала вся страница.

| viewport | было | стало |
| ---: | --- | --- |
| 270px | пейджер 292px в контейнере 254px, x −11…281 | 236px, x 17…253 |
| 280px | 292px в 264px, x −6…286 | 236px, x 22…258 |
| 320px | помещался | помещается |

Три правки:

- **Ниже 320px ужимаются пропорции** (кнопка 36px, многоточие 20px, зазор
  2px). Резать слоты дальше нельзя: следующими на выход шли бы первая и
  последняя страницы, а многоточие без них не значит ничего. Тач-цель
  становится 36×44 — вдвое выше минимума WCAG 2.2 (24×24).
- **Список стал контейнером прокрутки** (`overflow-x: auto` + отступ 2px под
  обводку фокуса): не влезшее листается внутри пейджера, а не растягивает
  документ. Клапан на будущее — четырёхзначные номера, чужие шрифты.
- **`justify-content: safe center`.** При переполнении обычный `center`
  срезает НАЧАЛО списка, и доскроллить до него нельзя в принципе. Объявлено
  двумя строками: браузер без поддержки `safe` отбросил бы всё правило и
  остался вовсе без центрирования.

320px — не произвольная граница: это ширина, на которой WCAG требует
обходиться без горизонтальной прокрутки (reflow при 400% зуме), и там набор
помещается как есть.

**Найдено попутно, не чинил:** на 270px документ всё равно на 2px шире
viewport, но пейджер тут ни при чём — тот же перебор есть на `/about`
(футер, индикатор загрузки), а на листинге за край уходят карточки клиник
(`clinic-info` до 280px). Отдельная история, ниже порога WCAG.
