## Итерация 1 — что сделано (2026-07-28)

Три файла:

- **`server/common/redirect/slug-redirects.ts`** — `try/finally` для освобождения соединения (раньше `end()` стоял внутри `try` после запросов и при ошибке соединение не возвращалось в пул) + `throw createError({ statusCode: 500 })` вместо `return null` **только для числовых ID**. Для обычных слагов поведение оставлено как было: там `null` действительно означает «редирект не нужен», и ронять основной трафик из-за упавшей проверки `slug_redirects` нельзя. Строгость введена ровно там, где 200 гарантированно неверен.
- **`pages/[...not-found].vue`** — `setResponseStatus(…, 404)`, `<title>`, `robots: noindex, follow`, `ErrorBlock` вынесен из `<ClientOnly>` в SSR.
- **`app.vue`** — canonical и hreflang-альтернативы не выводятся на catch-all роуте. Опознание по `route.params.notfound`: **дефис из имени файла Nuxt убирает**, поэтому не `not-found`; по `route.name` опознавать хуже — с i18n имя может получить локальный суффикс, параметр стабильнее.

**Опровергнуто по ходу:** заявленный soft-500 не существует, Nuxt отдаёт честный 500 — см. §1.3 итерации. Заодно выяснилось общее правило чтения выгрузок Яндекса: **колонка `httpCode` не описывает URL как он есть.**

**Не воспроизведено:** ветка «соединение получено, а запрос упал» (AC-1.3) — при сломанных кредах падает сам `getConnection()`, освобождать нечего. Happy path под нагрузкой проверен: 30/30 запросов на `/doctors/42` отдали 301, двойного `release()` в логе нет.

## Ревизия 2026-07-30 (ревью SEO-аудита)

Итерации 1–3 перепроверены по коду и на проде. **Код на месте и закоммичен (`6acf400`), тесты зелёные (54/54, `npx playwright test --project=unit`), на прод не выкатано** — подтверждено curl'ом: soft-404 всё ещё 200 (48 769 байт, без title, без noindex, self-canonical), `?tab=` всё ещё в canonical, в прод-sitemap всё ещё 2 статьи и 0 `/medications`. Пока не выкачено, итерацию 4 начинать нельзя (порядок из заголовка файла).

**Найдено два проявления того же класса, которых итерации не покрывают** (в скоуп этой PRD не входили — записаны в аудит как пункты 7d и 7e, `docs/audit/seo-2026-07.md`, баг 6):

- **Невалидное значение фильтра отдаёт полный листинг с self-canonical на мусорный URL.** `/doctors?specialtyIds=99999`, `?specialtyIds=abc`, `?cityIds=99999`, `/services?serviceCategoryIds=abc` → 200, заголовок с полным размером каталога (1316 / 5231), canonical на себя, без `noindex`. Итерация 3 нормализует **порядок** параметров, а не их **значения**, поэтому не помогает. Неограниченная дублирующая поверхность.
- **`?sort=` на подстраницах клиник индексируем.** `isFiltered` в `pages/clinics/[clinicSlug]/{services,labtests,medications,doctors}/index.vue` = `currentCategory != null || !!currentSearch`; `sort` не входит. Комментарий в `common/url-utils.ts` про «`sort` меняет состав страницы пагинации» верен для `?sort=X&page=2`, но `?sort=X` в одиночку остаётся дублем. Дешевле добавить `sort` в `isFiltered`, чем менять canonical.
- Проверено и **в порядке**: `?search=` на этих же подстраницах отдаёт `noindex, follow` и на пустой, и на непустой выдаче.

**Ещё одна находка, релевантная итерации 1 — ✅ уже закрыта.** 7 из 8 выкупленных доменов 301-или на **числовые** URL (`bolnica-meljine.me` → `/clinics/79` → слаг). Это был постоянный внешний источник числовых URL, не зависящий от аварии БД, и он объяснял клиническую часть (40 из 602) без всяких допущений. Реконструкцию про `catch → null` не отменяет — 558 из 602 приходятся на врачей, куда эти домены не ведут. Пользователь исправил редиректы 2026-07-30, проверено: все 8 отдают один 301 прямо на слаг, `www`/deep paths/`http://` тоже один хоп. Таблица «было/стало» — в `docs/audit/seo-2026-07.md`, раздел «Ссылочный профиль».

**Что это значит для базовой метрики ниже:** доля числовых URL в индексе Яндекса теперь имеет два независимых драйвера снижения — фикс `catch → null` (итерация 1, ждёт деплоя) и выпрямленные внешние 301 (уже в проде). Разделить их вклад по итоговому срезу будет нельзя. Для клиник (40 URL) сработает второй, для врачей (558) — только первый.

## Итерация 4 — приёмка на проде (2026-07-31)

- **Ключ-файл** `https://docta.me/89f50cfd…txt` — 200, верное содержимое, не редиректится даже с cookie `locale=ru`. Старый `a1b2c3d4…txt` — 404. `ads.txt` и `robots.txt` живы. Общее правило bypass «любой `.txt` в корне» работает.
- **robots.txt** — Cloudflare Managed **отключён пользователем**, блок `BEGIN Cloudflare Managed content` исчез. В файле: один `User-agent: *`, 18 `Disallow` (9 наших + 9 AI-ботов), 9 AI-групп, `Clean-param: tab`, `Content-Signal`, `Sitemap`. То есть цель итерации достигнута — у Яндекса больше нет повода игнорировать наш Disallow-список.
- **IndexNow: 602 URL отправлены, ответ 200 OK.** Первая попытка вернула 403 `SiteVerificationNotCompleted` — нормальное поведение для только что созданного ключа, повтор через несколько минут прошёл. Общий эндпоинт `api.indexnow.org` раздаёт всем участникам, то есть **Bing покрыт тем же запросом**, отдельной отправки не нужно. Google в протоколе не участвует.

**Ловушка, которая стоила диагностики: robots.txt кэшируется на эдже Cloudflare 4 часа.** Сразу после деплоя прод отдавал СТАРЫЙ файл (`cf-cache-status: HIT`, `Age: 519`, `last-modified: 11 Jun`), хотя ключ-файл выкатился мгновенно (`cf-cache-status: DYNAMIC` — его раньше никто не запрашивал, кэша не было). Проверять robots.txt после деплоя нужно в обход кэша: `curl "https://docta.me/robots.txt?cb=$RANDOM"`, иначе легко решить, что деплой не доехал.

## Довесок: снят ложный `lastmod` (2026-07-31, ЖДЁТ ДЕПЛОЯ)

Не входило в исходные 4 итерации, найдено при ответе на вопрос «а Bing тоже покроется».

`menuItemToLinks` ставил `lastmod: new Date()` каждой ссылке — все 13 638 URL заявляли, что изменились в момент запроса sitemap (13 638 тегов, 65 уникальных значений: дрейф миллисекунд при сборке). Это хуже отсутствующего `lastmod`: поисковик доверяет ему только если он стабильно правдив. И это важно именно для Google — **IndexNow он не поддерживает, `lastmod` был единственным рычагом переобхода, и мы его сами обнулили.**

Правка: `lastmod` в `SitemapLink` стал опциональным, нигде не заполняется, тег выводится только при непустом значении. Проверено на dev: 13 639 `<loc>`, **0 `<lastmod>`**, `changefreq` и 95 473 `xhtml:link` на месте, размер 13,5 → 12,8 МБ. Typecheck и prettier зелёные.

Правильное продолжение (не сделано): заполнять реальным `updated_at` сущности, для фасетных URL — максимумом по участникам. Тогда `lastmod` снова станет рабочим сигналом.

## Проверено и решено не чинить

- **Клик по табу не доезжает до роутера — `?tab=` теряется при смене языка.** Проверено 2026-07-28: баг существовал всегда, к итерации 3 отношения не имеет. `components/entity-page/tab-bar.vue` пишет параметр через `window.history.replaceState`, минуя vue-router, поэтому `route.query` остаётся без `tab`; `getLocalePath` в `components/language-switcher.vue` читает `route.query` и собирает URL без него. Теряется только после клика по табу — если пользователь пришёл на готовый `?tab=clinics`, параметр в `route.query` есть и переживает смену языка.
  **Не чиним:** табы — scroll-spy по анкорам, все секции всегда в DOM, поэтому «потеря таба» = страница осталась вверху, контент не скрыт. По SEO эффект нулевой (`tab` вырезается из canonical, в sitemap его нет). Дешёвой правки нет: перевод `updateQueryParam` на `router.replace` заводит навигацию посреди собственного плавного скролла компонента — `replaceState`, судя по всему, и выбран, чтобы не драться со скроллом роутера. Проверяется только в браузере, цена проверки выше цены баги.
