# Тихие 200: сервер отдаёт 200 там, где должен 301/404/500

**Приоритет:** P1 | **Статус:** 🟡 3.5/4 — итерации 1–3 **на проде** (2026-07-30), у итерации 4 готов код | **Источник:** [SEO-аудит июль 2026](../../docs/audit/seo-2026-07.md), раздел «Диагностика по Яндексу (2026-07-28)»

## Проблема

Найдено 2026-07-28 при разборе двух выгрузок Яндекс.Вебмастера (`data/yandex/`). Это не набор мелких SEO-правок, а **один класс дефектов: при сбое или отсутствии данных приложение деградирует тихо и отдаёт 200 вместо честного кода.** Поисковик 500 повторит, а 200 запомнит — и запись в индексе живёт годами.

**Масштаб, измеренный на индексе Яндекса (1434 страницы всего):**

| Проявление | Страниц в индексе | Доля индекса |
|---|---|---|
| Числовые URL, которые обязаны 301-иться | **602** | **42%** |
| Soft-404 (catch-all) | не измерить — поверхность неограниченная | — |
| ~~Страница 500 отдаётся с 200~~ | ❌ опровергнуто проверкой, см. §3 | — |

Для Google те же дефекты дают 7 622 «redirect», 830 × 404, 341 «Google выбрал другой canonical», 16 soft-404 в Coverage.

### 1. `catch → null` в `slug-redirects.ts` — 42% индекса Яндекса

[`server/common/redirect/slug-redirects.ts`](../../server/common/redirect/slug-redirects.ts) резолвит числовой ID в слаг запросом к БД. На любой ошибке:

```js
} catch (error) {
    console.error('Error checking slug redirect:', error);
}
return null;   // ← «редирект не нужен»
```

`null` для вызывающего middleware означает «редиректить не надо», запрос идёт дальше, и **числовой URL рендерится как обычная 200-страница с полным контентом.**

Что это даёт в индексе Яндекса: **602 URL** (558 `/doctors/*`, 40 `/clinics/*`, 2 `/medications/*`, 2 `/labtests/*`). Это **подмены, а не дубли** — выборка 41 URL из 602, разрешил редиректы, проверил наличие слаг-версии в индексе: **0 из 41**. Слаг-карточек врачей в индексе всего 358, то есть числовых URL больше, чем нормальных.

Реконструкция причины (не доказательство — воспроизвести отказы задним числом нельзя, но всё сходится):

1. Редирект появился 2026-04-01 (коммит `fe863cc` «slugs») и сейчас работает — проверено curl'ом.
2. 498 из 602 URL обойдены 30.05–01.06, уже после появления редиректа, и Яндекс получил 200 с корректным заголовком врача.
3. В том же окне была [утечка prepared statements](../../docs/audit/db-prepared-stmt-leak-2026-07.md) — запросы к БД падали.
4. Middleware редиректа открывает **своё** соединение раньше, чем страница — своё, поэтому при интермиттирующих отказах редирект глохнет, а страница успевает отрисоваться. Ровно наблюдаемая картина.

**Второй дефект в той же функции — утечка соединения.** `await connection.end()` (в этом проекте `end()` пропатчен в `release()`) стоит **после** запросов, без `try/finally`. Если запрос упал — соединение не возвращается в пул. При `connectionLimit: 10` и `queueLimit: 0` (очередь неограниченная) десяти таких ошибок хватает, чтобы пул умер, а все последующие запросы встали в очередь навсегда — до рестарта pm2. Это объясняет форму аварии лучше, чем одно исчерпание `max_prepared_stmt_count`.

### 2. Soft-404: catch-all отдаёт 200

[`pages/[...not-found].vue`](../../pages/[...not-found].vue) на любой несуществующий путь верхнего уровня (`https://docta.me/no-such-page-xyz123`, проверено на проде 2026-07-28) отдаёт **HTTP 200**, 48 КБ HTML, и при этом:

- **нет `<title>`** вообще;
- **нет `noindex`**;
- `<link rel="canonical">` указывает на сам несуществующий URL;
- текст ошибки обёрнут в `<ClientOnly>`, поэтому **в SSR-HTML про ошибку нет ни слова** — краулер видит шапку, полную навигацию и футер.

Для поисковика это тонкая, но валидная страница с меню сайта. Поверхность неограниченная: любая опечатка, любая ссылка от спамера, любой мёртвый URL становится индексируемой 200-страницей.

Страницы сущностей при этом сделаны правильно — `pages/labtests/[labTestSlug]/index.vue:49-51` и ещё 14 таких же мест:

```js
if (import.meta.server && !isFound.value) {
	setResponseStatus(useRequestEvent()!, 404);
}
```

То есть паттерн в проекте есть, catch-all просто из него выпал.

### 3. ~~Soft-500~~ — опровергнуто проверкой 2026-07-28

Дефолтная страница ошибки Nuxt («500 - Internal Server Error | Nuxt») присутствует в индексе Яндекса как `SEARCHABLE` с `httpCode 200` — 7 URL, в логе добавлений 12. **Из этого был сделан неверный вывод, что страница ошибки отдаётся с кодом 200.**

Прямая проверка (страница с `throw` на dev, `Accept: text/html`) даёт `HTTP 500` и `<title>500 - Server Error | Nuxt</title>`. Soft-500 не существует, `error.vue` не нужен.

Правильное чтение: **колонка `httpCode` у Яндекса не описывает URL как он есть** — доказано независимо тем, что числовые URL, отдающие 301, тоже перечислены с `httpCode 200`. У этих 7 строк устарел заголовок (снят при обходе во время аварии), код 200 — от позднего успешного обхода. Освежится переобходом (итерация 4).

| Обход | URL |
|---|---|
| 25.07 | `/doctors?lang=ru&specialtyIds=4` / `=2` / `=17` |
| 25.07 | `/doctors/toma-nisavic?lang=ru` |
| 23.07 | `/doctors/sinisa-glumicic?lang=ru` |
| 16.07 | `/services/co2-laser-face?lang=ru` |
| 16.07 | `/services/prp-treatment-for-intimate-rejuvenation-women-and-men?lang=ru` |

Побочно: у пяти обход 23 и 25 июля, то есть **на дату фикса утечки (`8039957`, 23.07) и после неё** — фикс не закрыл проблему целиком либо была вторая причина. Разбор логов за 23–27.07 в скоуп этой PRD не входит, вынесен в бэклог аудита.

### 4. 15 из 17 статей отсутствуют в sitemap

[`server/common/sitemap/sitemap.ts:102-105`](../../server/common/sitemap/sitemap.ts) — `articleList` захардкожен:

```js
const articleList = [
	'russian-speaking-doctors-in-montenegro',
	'clinics-with-language-support',
];
```

В `pages/articles/` при этом 17 статей. **В индексе Яндекса ровно эти две и ничего больше** — то есть для Яндекса sitemap здесь и есть канал обнаружения, а листинг `/articles` как точка входа не работает. Это те же страницы, которые в пункте 1a аудита сделаны хабами перелинковки на карточки сущностей, и на которые опирается пункт 5 (E-E-A-T).

Отдельно: `/medications/[slug]` (33 карточки лекарств в клиниках) в sitemap отсутствуют целиком — генератор выдаёт только `/clinics/*/medications`-подстраницы. Яндекс нашёл и держит 32 таких URL сам.

### 5. Canonical: два воспроизводимых дубля

- **Порядок фасетных параметров не нормализуется.** `?specialtyIds=4&cityIds=1&lang=ru` и `?cityIds=1&specialtyIds=4&lang=ru` отдают два разных self-canonical на идентичный контент. `lang` при этом нормализуется корректно (всегда уезжает в конец) — механизм есть, не хватает сортировки остальных параметров.
- **`?tab=clinics` self-canonical.** 6 таких URL в индексе Яндекса (`/labtests/{alkaline-phosphatase,cholesterol,ck}?tab=clinics` в en и ru). `tab` — чисто UI-параметр, его нет ни в sitemap, ни в серверном HTML: Яндекс нашёл его, исполнив JS.

## Scope

**В скоупе:** 4 подтверждённых дефекта выше + утечка соединения в `slug-redirects.ts`. Пятый заявленный (soft-500) проверен и опровергнут.

**Не в скоупе:**

- **Систематическая утечка соединений во всех остальных эндпоинтах.** `getConnection()` вызывается напрямую примерно в 80 файлах, и ни в одном из проверенных (`services/details.ts`, `doctors/list.ts`, `clinics/details.ts`, `redirect/doctor-redirects.ts`) нет `try/finally` — освобождение соединения зависит от happy path. `executeQuery` в `db-mysql.ts` сделан правильно, через `finally`. Это отдельная и, возможно, более важная задача (реальная причина падений прода), но она не про индексацию и требует своего разбора — **см. итерацию 5 в бэклоге, не делать здесь.**
- **Разбор логов за 23–27.07** по хвосту падений — в бэклоге аудита.
- **Сокращение фасетной поверхности.** Пункт 3 аудита урезан трижды: у Google фасеты дают 29% показов, у Яндекса их в индексе ~25 штук. Резать нельзя, только canonical.
- **IndexNow, `Clean-param`, слияние блоков `User-agent: *` в robots.txt, `sr-Cyrl` в hreflang** — вынесено в отдельную итерацию 4, потому что это не баги, а ускорение переобхода; без него правки 1–3 проявятся только когда Яндекс сам дойдёт (602 URL не обойдены с 01.06).

## Acceptance Criteria (сводные)

Детальные AC — в файлах итераций. Общие требования ко всем:

- AC-0a: `npm run typecheck` зелёный после каждой итерации.
- AC-0b: Каждая итерация проверена на dev-сервере curl'ом по кодам ответа, а не только по коду. **Коды ответа нельзя проверять глазами в браузере** — браузер покажет ту же страницу и для 200, и для 404.
- AC-0c: Ни одна правка не меняет то, что видит живой пользователь на существующих рабочих страницах. Все изменения — в HTTP-статусах, `<head>` и sitemap.

## Как проверять (общие ловушки)

- Локаль на проде задаётся `?lang=ru`, а не префиксом пути (`/ru/...` отдаёт 200 с пустой оболочкой). См. [[prod-check-gotchas]].
- Только `curl -o /dev/null -w "%{http_code}"`, не node fetch.
- Для 301 смотреть `%{redirect_url}` **без** `-L`, иначе увидишь код цели, а не редиректа.
- Сравнивать HTML именно серверный (`curl`), а не отрендеренный в браузере — половина найденных дефектов в том, что в SSR-HTML чего-то нет.
